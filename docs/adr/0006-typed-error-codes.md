# ADR-0006: Typed Error Classes with Machine-Readable Codes

- Status: Accepted
- Date: 2026-10-26
- Deciders: Valentín Flórez Arbeláez

---

## Context

The codebase originally used generic `throw new Error("message string")` for all
error conditions. This pattern has several systemic problems:

- **Unprogrammable** — callers must parse message strings with `includes()` or
  regex to distinguish error types, which is fragile and locale-sensitive.
- **No `instanceof` narrowing** — `catch (e)` blocks cannot type-narrow to a
  specific error subclass; every handler must defensively check `e.message`.
- **No catalog** — there is no authoritative list of error conditions the system
  can produce. Monitoring dashboards, error budgets, and runbooks cannot be
  derived from the code.
- **Telemetry gaps** — structured logging systems (e.g., DataDog, OpenTelemetry)
  benefit from a stable `error.code` field; free-form messages produce high-
  cardinality noise.
- **MCP protocol friction** — MCP clients expect structured error payloads with
  stable codes for retry/circuit-breaker logic; message strings require
  re-parsing at the protocol boundary.

---

## Decision

### Domain errors: `ContractError` hierarchy

Domain-layer errors (logic violations) extend `ContractError` from
`eosKernelPrimitives.ts`, categorized by contract type:

```typescript
export type ContractKind = "PRECONDITION" | "POSTCONDITION" | "INVARIANT";

export class ContractError extends Error {
  constructor(
    readonly kind: ContractKind,
    message: string,
    readonly context?: Record<string, unknown>
  ) {
    super(`[${kind}] ${message}`);
    this.name = "ContractError";
  }
}
```

### Infrastructure errors: typed subclasses with `code`

Infrastructure-layer errors extend a base `EosError` class and carry a
`readonly code: string` field with a stable, namespaced identifier:

```typescript
export abstract class EosError extends Error {
  abstract readonly code: string;
}

export class ToolNotFoundError extends EosError {
  readonly code = "EOS_MCP_TOOL_NOT_FOUND" as const;
  constructor(readonly toolName: string) {
    super(`MCP tool not registered: ${toolName}`);
    this.name = "ToolNotFoundError";
  }
}

export class FleetProjectNotFoundError extends EosError {
  readonly code = "EOS_FLEET_PROJECT_NOT_FOUND" as const;
  constructor(readonly projectKey: string, readonly resolvedPath: string) {
    super(`Fleet project '${projectKey}' not found at '${resolvedPath}'`);
    this.name = "FleetProjectNotFoundError";
  }
}
```

### `Result<T, E>` for fallible operations

Functions that can fail without exceptional conditions return
`Result<T, E>` rather than throwing:

```typescript
export type Result<T, E extends EosError = EosError> =
  | { ok: true;  value: T }
  | { ok: false; error: E };
```

Throwing is reserved for unrecoverable programming errors (contract violations).
Recoverable failures (tool not found, project path missing) return `Result`.

Error code prefixes by subsystem:
- `EOS_MCP_*` — MCP server and tool dispatch
- `EOS_FLEET_*` — fleet auditor and dispatcher
- `EOS_KERNEL_*` — kernel primitives and health
- `EOS_AUTH_*` — authentication and authorization
- `EOS_CICD_*` — CI/CD pipeline integration

---

## Consequences

**Positive:**
- Callers use `instanceof ToolNotFoundError` or `result.error.code ===
  "EOS_MCP_TOOL_NOT_FOUND"` — no string parsing.
- An error catalog can be auto-generated by scanning for `readonly code =`
  declarations across the codebase.
- Stack traces are fully preserved (`super(message)` chain is intact).
- MCP error responses can embed `code` directly in the structured payload.
- TypeScript ensures `code` is a literal type — accidental typos are compile
  errors.

**Negative / Trade-offs:**
- More boilerplate per error type (a dedicated class file or block per error
  condition).
- Developers must choose between `throw` and `Result` — requires a documented
  convention (recoverable → `Result`, unrecoverable → `throw`).
- Existing `throw new Error(...)` callsites must be migrated incrementally.

---

## Rejected Alternatives

| Alternative | Reason Rejected |
|---|---|
| **Union error types only (no `instanceof`)** | Discriminated unions work well for `Result` but cannot be used in `catch` blocks; a class hierarchy covers both use cases. |
| **Error codes as plain `string` field** | `error.code = "some_string"` has no type safety; literal type `"EOS_MCP_TOOL_NOT_FOUND"` is checked by the compiler and IDE. |
| **Numeric error codes** | Human-unreadable without a lookup table; string codes are self-documenting in logs and stack traces. |
| **Single error class with `type` discriminant** | Loses `instanceof` narrowing and forces every handler to use a switch statement rather than a catch clause. |
| **Never throw, always `Result`** | Makes unrecoverable programming errors (broken invariants) indistinguishable from expected recoverable failures at the call site. |
