## 1. Architectural Strategy & ADRs

### ADR-163-01: Native Hardware Enclave Architecture & PCR Measurement Model

- **Context**: In autonomous engineering systems, sensitive assets (signing certificates, release private keys, deployment tokens, and sovereign agent identities) must execute in isolation from the host OS, virtualization hypervisors, and cloud administrators. Hardware TEEs (AWS Nitro Enclaves, AMD SEV-SNP, Intel SGX/TDX) provide isolated address spaces with memory encryption.
- **Decision**: Implement a native, zero-dependency Platform Configuration Register (PCR) measurement model conforming to AWS Nitro and AMD SEV-SNP standards:
  - `PCR0`: Cryptographic SHA-256 measurement of the enclave image file (EIF), kernel, and runtime bootloader.
  - `PCR1`: SHA-256 measurement of kernel command line options and boot arguments.
  - `PCR2`: SHA-256 measurement of application code bundles, packages, and configuration manifests.
  - `PCR8`: SHA-256 measurement of IAM role, instance profile, or cloud security context.
- **Alternatives Considered & Rejected**:
  - _Installing third-party TEE SDKs (`aws-nitro-enclaves-sdk-c` / `@aws-sdk/client-kms`)_: Rejected due to **Law V** violation.
  - _Software-only key storage in `.env` or files_: Rejected because host root or hypervisor snapshot can read memory in cleartext.

### ADR-163-02: Cryptographic Remote Attestation Protocol & Root of Trust

- **Context**: A remote orchestrator or CI/CD coordinator must mathematically prove that code running inside an enclave has not been tampered with before entrusting it with confidential workloads.
- **Decision**: Implement an attestation document structure signed by a hardware Root-of-Trust (RoT) key pair (AWS Nitro Root CA or AMD KDS). The document bundles:
  - `moduleName` & `enclaveId`.
  - `timestamp`: Enclave creation/issuance timestamp.
  - `nonce`: Cryptographically secure caller-supplied nonce ensuring freshness and preventing replay attacks.
  - `pcrs`: Map of measured registers (`pcr0`, `pcr1`, `pcr2`, `pcr8`).
  - `publicKey`: Ephemeral public key generated inside the enclave for secure key exchange.
  - `signature`: Ed25519 or ECDSA signature over the canonical attestation payload generated by the hardware RoT.
- **Verification Rule**: A coordinator validates the RoT signature, verifies that the nonce matches the requested challenge, and asserts that PCR0/PCR2 match the authorized baseline hash.

### ADR-163-03: Measurement-Bound Secret Sealing via HKDF-SHA256 and AES-256-GCM

- **Context**: Secrets stored on persistent disk must be indecipherable to anyone outside the exact hardware enclave.
- **Decision**: Derive an enclave-specific sealing key using HKDF-SHA256:
  $$K_{seal} = \text{HKDF}(\text{IKM}=\text{RootEnclaveSecret}, \text{Salt}=\text{EnclaveSalt}, \text{Info}=\text{"eos-tee-seal"} \mathbin{\Vert} \text{PCR0} \mathbin{\Vert} \text{PCR2})$$
  Encrypt payloads using AES-256-GCM with a random 12-byte IV and 16-byte authentication tag.
  If an adversary attempts to unseal the secret on a modified binary or compromised kernel, the resulting PCR0/PCR2 mismatch produces a completely different $K_{seal}$, causing GCM tag authentication to fail fail-closed with `ENCLAVE_MEASUREMENT_MISMATCH`.

## 3. Invariants & Guardrails

- **Law V**: Zero runtime third-party dependencies (`dependencies: {}`) using Node.js built-in `node:crypto`.
- **SPEC-250**: Each module must strictly maintain $\le 800$ lines with $\ge 12$ lines of headroom.
- **Fail-Closed Execution**: Any measurement drift or signature invalidation immediately rejects execution.
